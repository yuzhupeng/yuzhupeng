# Agent Harness + 状态机 + 链表 + 提示词工程：业务流程Agent架构设计

面向**报价、财务结算、品质异常、来料异常**这类强规则、多步骤、需要回溯、分支跳转、可审计的流程性业务场景。

> 
> 核心痛点：普通大模型Agent容易跳步骤、漏审批、状态丢失、上下文混乱；传统硬编码状态机改流程成本高。
> 组合思路：
> 
> 
> 1. **Agent Harness**：Agent运行时框架，接管大模型调用、工具调度、记忆、异常捕获、事件分发；
> 2. **有限状态机FSM**：定义流程节点、流转条件、分支、审批；
> 3. **双向链表**：保存流程历史快照，支持回退、跳转、断点续跑、审计溯源；
> 4. **提示词工程**：分层提示，区分角色提示、节点提示、工具调用提示、校验提示，大模型只做节点内推理，**不允许大模型私自修改流程拓扑**。

## 整体架构总览

```
┌─────────────────────────────────────────────────────┐
│                业务输入层（用户/工单/IM）              │
└───────────────────┬─────────────────────────────────┘

│  • 会话管理、事件队列、工具注册、错误恢复、日志审计     │

└───────────┬──────────────────────────────┬──────────┘
            ▼                              ▼

```

### 关键设计原则（非常重要）

> 
> ❌禁止：大模型自由决定下一步走到哪个状态，会乱流程。
> ✅规则：**状态流转的分支判断权交给状态机；大模型只负责当前节点内的业务推理、信息提取、内容生成、工具调用；下一步由状态机根据输出结果+配置条件驱动**。
> 链表只负责**实例历史存储、回溯、审计**，不定义流程拓扑。

## 1. Agent Harness 设计（Agent运行基座）

Harness是整个系统的“容器”，隔离大模型、业务流程、外部工具，避免LLM直接操作业务。

### Harness核心模块

1. **流程实例管理器**
   - 每个业务工单对应一个`ProcessInstance`，绑定唯一ID；
   - 持有：FSM定义引用、双向链表头/尾指针、当前节点指针、全局业务上下文。
2. **事件驱动引擎**
   - 事件：用户输入、工具返回、审批完成、超时、异常报错；
   - 事件送入队列，驱动状态机流转。
3. **工具注册&沙箱**
   - 所有外部操作（查库存、生成报价单、推送钉钉、写数据库）全部注册为工具；
   - LLM只能调用注册工具，不能直接访问业务库。
4. **错误与断点恢复**
   - LLM输出异常、工具报错、网络中断，保存当前链表快照；支持后续恢复继续跑。
5. **审计日志**
   - 每一步：输入、LLM输出、工具调用、状态变更、时间戳全部写入链表节点。

### Harness执行循环伪代码

```
# Agent Harness主循环
def run_process(instance_id, user_input):
    instance = harness.get_instance(instance_id)
    # 将用户输入写入当前链表节点
    instance.append_user_input(user_input)

    while True:
        current_state = instance.fsm.get_current_state()
        # 1.加载当前节点专属提示词
        prompt = build_prompt(current_state, instance.get_context())
        # 2.调用LLM推理，仅处理当前节点业务
        llm_output = llm.call(prompt, tools=current_state.tools)
        # 3.执行工具调用
        tool_result = harness.exec_tools(llm_output.tool_calls)
        # 4.把llm输出、工具结果写入链表节点
        instance.append_llm_snapshot(llm_output, tool_result)
        # 5！关键：由状态机做流转判断，不是LLM决定！
        next_state, condition_result = instance.fsm.transition(
            current_state, llm_output, tool_result
        )
        # 更新链表：新增下一个节点
        instance.link_next_node(next_state, condition_result)
        # 状态机终止，流程结束
        if next_state.is_terminal():
            return instance.get_final_result()
        # 外部等待（等待人工审批、等待用户回复），挂起流程
        if next_state.is_wait_human():
            instance.suspend()
            return "等待人工交互"
```

## 2. 有限状态机FSM：定义业务流程拓扑

FSM是**静态流程蓝图**，预先定义报价、来料异常、财务结算的全部节点、流转条件。

> 
> 示例：来料异常流程节点定义

```
S0:初始化(接收来料异常工单)
S1:信息补全（缺失物料、批次、不良现象，向用户收集）
S2:不良判定（调用工具查BOM、质检记录；LLM做信息分析）
S3:责任判定分支
    ├─条件：供应商责任 → S4发起供应商索赔审批
    ├─条件：内部制程问题 → S5内部整改流程
    └─条件：误判 → S9流程结束关闭
S4:索赔审批节点【人工审批】
    ├─审批通过 → S6生成扣款单推送财务
    └─审批驳回 → S3重新责任判定
S5:内部整改
S6:财务入账
S9:流程结束
```

### FSM数据结构设计

```
{
  "process_key": "incoming_material_abnormal",
  "states": [
    {
      "state_id": "S0",
      "name": "流程初始化",
      "prompt_ref": "prompt_incoming_S0",
      "tools": [],
      "is_wait_human": false
    },
    {
      "state_id": "S1",
      "name": "信息补全",
      "prompt_ref": "prompt_incoming_S1",
      "tools": [],
      "is_wait_human": true
    }
  ],
  "transitions": [
    {
      "from": "S0",
      "to": "S1",
      "condition": "context缺少物料编码 or 缺少不良描述"
    },
    {
      "from": "S0",
      "to": "S2",
      "condition": "所有必填字段完整"
    }
  ]
}
```

- `prompt_ref`：引用提示词库中对应节点的提示词；
- `condition`：可以是简单表达式，也可以调用LLM做条件判断（但判断结果交给FSM，LLM不能选state_id）。

## 3. 双向链表：流程实例快照存储

FSM是蓝图；**链表是每一份工单的运行实例**。

> 
> 为什么用链表，而不是普通数组：
> 1.流程会回退（审批驳回，回到上一个责任判定节点）；
> 2.可插入临时节点（中间新增复核节点）；
> 3.每一个节点保存完整快照，审计溯源；
> 4.断点续跑：挂起之后，可以从链表任意节点恢复执行。

### 链表节点结构

```
class ProcessNode:
    node_id: str
    prev: Optional[ProcessNode]   # 上一步
    next: Optional[ProcessNode]    # 下一步
    state_id: str                 # 当前FSM状态
    timestamp: datetime
    user_input: str               # 用户输入
    llm_prompt: str               # 本次使用的提示词
    llm_output: Any               # LLM输出
    tool_calls: List              # 工具调用记录
    tool_results: List            # 工具返回
    context_snapshot: dict        # 业务上下文快照（物料、金额、不良信息等）
    remark: str                   # 备注，驳回原因、人工批注
```

### 链表支持能力

1. **正常流转**：append_next，新增节点向后走；
2. **回退（驳回）**：`goto_prev(node_id)`，指针切回历史节点，重新执行；
3. **插入节点**：在A、B节点中间插入复核节点；
4. **快照回放**：遍历整条链表，完整复现整个工单每一步发生了什么；
5. **断点续跑**：实例挂起时，`current_pointer`指向链表当前节点，唤醒后从该节点继续跑。

> 
> ⚠️链表只记录实例，**不能修改FSM的流程拓扑**。链表可以走到FSM已定义的状态，不能凭空生成不存在的state。

## 4. 分层提示词工程设计

核心：**禁止一个大Prompt包揽全部流程；每个FSM节点对应一套提示词**，基座提示词统一约束Agent行为。

### 四层提示词体系

1. **【全局基座提示词】（所有节点共用）**> 
> 约束Agent行为，最重要，防止乱跳流程。

```
# 全局基座约束
你是业务流程Agent，运行在Agent Harness+状态机系统中。
重要规则：
1.你**不能自己决定下一步跳转到哪个流程节点**。你的职责仅处理【当前状态】内的业务任务。
2.只允许调用分配给当前状态的工具，禁止调用其他工具。
3.所有输出必须结构化输出json，不要编造业务数据，缺失信息如实标记。
4.如果信息不足，输出{need_more_info:true, missing_fields:[xxx]}，由系统触发向用户收集信息。
5.禁止私自跳过审批节点，禁止私自结束流程。流程流转、跳转、回退全部交给外层状态机引擎。
6.所有业务推理结果，必须输出可被机器解析的结构化字段，方便状态机做条件判断。
```

2. **【节点专属提示词】每个State独立Prompt**
示例：来料异常S2“不良判定”节点提示词

```
## 当前状态：S2 来料不良判定
业务目标：基于已收集的物料编码、批次、不良现象，结合质检记录，完成不良现象分析。
需要输出结构化JSON：
{
  "abnormal_type":"",
  "abnormal_level":"严重/一般/轻微",
  "suspect_responsibility":["供应商","内部制程","误判"],
  "analysis_comment":"分析描述"
}
可用工具：query_quality_record(物料编码，批次号)
```

3. **【工具调用提示词】**：统一工具描述、入参出参格式；
4. **【校验提示词】**：对LLM输出做校验，比如金额校验、必填字段校验，输出校验结果给状态机做条件。

> 
> 好处：改业务逻辑，只需要修改对应节点提示词，不用修改Harness和状态机引擎代码；新增流程，新增一套FSM定义+一批节点提示词。

## 5. 业务场景落地示例

### 场景1：报价流程

- FSM节点：初始化→收集客户/物料/数量信息→查成本工具→生成报价草稿→人工审批报价→对外输出报价单→流程结束；
- 链表：每一步保存报价草稿快照，审批驳回，指针切回“生成报价草稿”节点重新计算；
- Harness：调用物料查询、成本查询、推送审批工具。

### 场景2：来料品质异常

- FSM节点：工单接收→信息补齐→不良判定→责任分支→审批→扣款/整改→结束；
- 链表完整记录每一轮判定、驳回、修改；审计可以直接遍历整条链表看完整处理链路。

### 场景3：财务结算流程

- FSM：接收结算单→校验单据完整性→匹配入库单/发票分支→异常处理节点→财务审核→生成付款申请→结束；
- 遇到单据缺失，状态机停在信息补全节点，等待用户补充，链表记录每一次校验快照。

## 6. 优势对比

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 纯LLM自由Agent | 开发快 | 乱跳步骤、漏审批、不可审计，业务流程不可控 |
| 硬编码状态机 | 稳定可控 | 业务一变就要改代码，上线慢 |
| **Agent‑Harness+状态机+链表+提示词** | ✅流程拓扑由FSM管控，LLM不能乱跳   ✅提示词驱动业务逻辑，改流程不用改底层代码   ✅链表完整快照，支持驳回、回退、审计、断点续跑   ✅Harness统一管控工具调用、异常、日志 | 需要前期搭建Harness与FSM引擎，有一定开发成本 |

## 7. 可扩展优化点

1. **FSM支持子流程**：比如品质异常内部嵌套“供应商索赔子流程”；
2. **提示词版本管理**：每个节点prompt做版本，A/B测试；
3. **人机协同**：状态机标记`wait_human`，流程挂起，人处理完事件再唤醒harness继续执行；
4. **条件判断增强**：简单条件用表达式，复杂业务判断交给LLM输出布尔字段，交给FSM做流转；
5.持久化：FSM定义存配置库；链表节点序列化存入数据库，工单重启不会丢失。

## 8. 潜在风险与规避

1. **风险：LLM输出错误，导致状态机条件判断错误**> 
> 规避：增加输出校验提示词，关键业务字段增加工具二次校验，设置阈值，关键审批节点强制人工介入。
2. **风险：Prompt膨胀，上下文太长**> 
> 规避：链表支持快照压缩，只把当前节点+必要业务上下文喂给LLM，历史只用于审计，不全塞进prompt。
3. **风险：Prompt改动破坏流程**> 
> 规避：基座提示词固定，节点prompt只改业务内容，**禁止节点prompt修改全局约束规则**。
